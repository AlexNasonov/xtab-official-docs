## Журнал аудита

Журнал аудита только дополняется. Записи связаны цепочкой хешей, контрольные точки подписываются ключом `secrets/audit_signing_key`, которого нет в базе. Проверка цепочки считает нарушением контрольную точку без подписи этого ключа, поэтому ключ нельзя терять и заменять: с новым ключом прежние точки перестанут проходить проверку. Ежемесячный архив шифруется ключом `audit_archive_key`, узлы получают только его открытую часть. Ключ подписи есть только у сервиса `xtab-sealer`: у узла фоновых задач, который меняет схему базы и разбирает загруженные файлы, его нет, поэтому взлом этого узла не позволяет подделать подписанные контрольные точки. Резервные копии и архив журнала подписывает другой ключ — `secrets/files_signing_key`; копии и архивы, сделанные до v0.9, проверяются прежним ключом аудита. Узел фоновых задач раз в сутки проверяет цепочки по открытой части ключа аудита — переменной `XTAB_AUDIT_PUBLIC_KEY` в `.env`, её пишет установщик. Если её нет (установка, собранная вручную), `xtab doctor` на узле фоновых задач предупреждает, а подписи контрольных точек не проверяются; значение выводит `docker compose exec xtab-sealer xtab audit public-key` (строка «public key»). В предварительных версиях v0.9 узел фоновых задач сверял точки не с тем ключом и поднимал ложную тревогу «цепочка нарушена»; после обновления закройте эту тревогу — следующая суточная проверка целой цепочки её не повторит.

```bash
docker compose exec xtab-sealer xtab audit verify            # целостность цепочки и подписей
docker compose exec xtab-worker xtab audit export > audit.jsonl
age -d -i secrets/audit_archive_key <месяц>.jsonl.age        # чтение архива утилитой age
```

Выгрузка в SIEM (syslog по TLS) настраивается администратором организации на странице «Журнал аудита».

## Смена ключей

Команды выполняются в каталоге установки.

**Ключ организации** — им запечатаны её секреты: ключи автоматизаций, приложений-аутентификаторов, клиентов SSO. Смена — без остановки:

```bash
docker compose run --rm migrate keys rotate-org
```

Без `--org N` меняются ключи всех организаций.

**Главный ключ** (`secrets/master_key`) — им обёрнуты ключи установки и организаций. Узлы держат его в памяти, поэтому на время смены они останавливаются:

```bash
od -An -tx1 -N32 /dev/urandom | tr -d ' \n' >secrets/master_key.new
docker compose stop xtab xtab-worker
docker compose run --rm -v "$PWD/secrets/master_key.new:/run/secrets/master_key_new:ro" migrate keys rotate-master --new-key-file /run/secrets/master_key_new
cp secrets/master_key secrets/master_key.old
cat secrets/master_key.new >secrets/master_key && rm secrets/master_key.new
docker compose up -d
```

Ключи переворачиваются одной транзакцией: при ошибке ничего не меняется, узлы запускаются со старым ключом. Резервные копии, снятые до смены, открываются только старым ключом — храните `master_key.old` отдельно от них, пока копии нужны.

После отката на прежнюю версию без восстановления копии смена ключей недоступна, пока не установлена версия, которой принадлежит база: ключи меняет только версия той же схемы. Команда откажет с сообщением «database schema version … is ahead of this binary … install the version the database belongs to».

## Рекомендации

- Ограничьте вход на сервер и доступ к каталогу установки: у кого есть `secrets/` и консоль, у того полные права на установку.
- Включите второй фактор для всех пользователей политикой организации, а не только для администраторов.
- Храните `secrets/master_key`, `backup_key` и ключи аудита вне сервера и вне копий: в сейфе или хранилище секретов организации.
- Держите копии на S3 другой машины и проверяйте восстановление раз в квартал.
- Подключите алерты из `monitoring/` и выгрузку аудита в SIEM.
